## 2. 关键修复

### 2.1 `UNREGISTER_CLIENT` 的 body 为空

RocketMQ 4.9.x `MQClientAPIImpl.unregisterClient()` 把 `clientID` 放在 **extFields**：

```java
UnregisterClientRequestHeader requestHeader = new UnregisterClientRequestHeader();
requestHeader.setClientID(clientID);
requestHeader.setProducerGroup(producerGroup);
requestHeader.setConsumerGroup(consumerGroup);
```

最初只解析 body，导致旧 client 永远留在 registry；第二次 Push 启动时 rebalance 把 8 个 queue 分给“旧 client + 新 client”，新 client 只能拿到部分 queue。

修复：优先读 `extFields.clientID`，再回退 body。日志出现：

```text
client unregistered client_id="198.18.0.1@17024#..."
```

### 2.2 长轮询

`PULL_MESSAGE` 的 `suspendTimeoutMillis` 来自 Push 消费者（默认 20s）。R2 先实现 1s 上限：

```text
read -> empty -> wait(notify or 1s) -> read again -> response
```

`BrokerStore::append` 后 `Notify::notify_waiters()`，避免 Push 线程忙轮询。

### 2.3 消费者 TTL

`consumers: HashMap<group, HashMap<clientId, Instant>>`；`consumer_ids` 只返回 60s 内有心跳的 client。  
这解决异常退出/来不及 unregister 时的僵尸 client 问题；正常 shutdown 仍以 `UNREGISTER_CLIENT` 为主。


### 3.4 失败重投 smoke

```text
RETRY ATTEMPT 1 reconsume=0 body=hello-retry
RETRY ATTEMPT 2 reconsume=1 body=hello-retry
RETRY RESULT attempts=2 ok=true
```

链路：`RECONSUME_LATER` → 客户端发 `CONSUMER_SEND_MSG_BACK` → Broker 写入 `%RETRY%group`（`reconsumeTimes+1`）→ Push 消费者再次拉取。

### 3.5 二进制持久化与性能

CommitLog 持久化从 JSON 切换为 `StoredMessage::encode`：

```text
发送 15 条 -> 杀 Broker -> 同一 store-root 重启 -> PullOnly received=15 expected=15
```

1KiB、4 线程、同步发送 benchmark：

| 版本 | TPS | 平均 RT | Max RT | 失败 |
|---|---|---|---|---|
| JSON 持久化 | 277 | 14.5ms | 863ms | 0 |
| 二进制持久化 | **1,261** | 3.1ms | 370ms | 0 |

> 仍是 Windows 开发机 + debug 构建；仅证明相对提升，不作为 1.0 性能验收。

### 3.7 重复消费说明

Push 消费是 **至少一次**。客户端 offset 持久化是周期性的（默认 5s），进程异常退出/快速重启可能出现重复消费；R2 smoke 使用新 topic 验证功能，重复消费由 Inbox/幂等（R4）兜底。

### 3.7 DLQ（本轮打通）

```text
DLQ ATTEMPT 1
DLQ ATTEMPT 2
DLQ RECV hello-dlq reconsume=2
DLQ RESULT attempts=2 dlq=1 topic=%DLQ%mq_rust_dlq_group_...
```

Broker：

```text
message sent back ... retry_topic=%RETRY%... reconsume_times=1 dlq=false
message sent back ... retry_topic=%DLQ%...  reconsume_times=2 dlq=true
```

两个根因：

1. **长轮询阻塞连接**：8 个 `PULL_MESSAGE` 串行占用同一连接，`CONSUMER_SEND_MSG_BACK` 排队超时。已把 `PULL_MESSAGE` 放到独立 task，不再阻塞 send/ack。
2. **重试计数永远从 0 开始**：客户端 send-back 始终带原始 `originMsgId`，Broker 按 origin 的 `reconsume_times` 递增会一直是 1。改为按 `originMsgId` 维护单调 `retry_counts`。

### 3.8 SQL92 属性过滤（本轮打通）

```text
SQL92 PUSH RECV expensive price=150
SQL92 PUSH RESULT count=1
```

两个前置条件：

1. **`CHECK_CLIENT_CONFIG`（46）**：SQL92 消费者启动时先发 code 46；Broker 需返回成功，否则 `unsupported request code 46`。
2. **订阅数据不在 Pull 请求里**：4.9.8 客户端 `postSubscriptionWhenPull=false`，Pull 只带 `subVersion` 和 `expressionType=SQL92`。  
   修复：从 `HEART_BEAT.consumerDataSet[].subscriptionDataSet` 保存 `(group, topic) -> (subString, expressionType)`，Pull 时补全。

过滤器支持：比较、`AND/OR/NOT`、括号、`IS [NOT] NULL`、`[NOT] IN`、`[NOT] BETWEEN`。
