# R35 · 性能实验（多连接 / 索引写优化）

> 日期：2026-11-25  
> 结论：两项实验均未超过 9,347 TPS，已回退索引改动。

---

## 1. 多连接测试

4 个 Producer 进程 × 4 线程 × 25k：

```text
每个 TPS：1774 / 1808 / 1803 / 1744
总消息：100,000
总墙钟：40.28s
聚合 TPS：≈ 2,482（按总墙钟）／≈7,129（各进程 TPS 之和）
```

低于单连接 100k 的 **9,347 TPS**，说明单 CommitLog 锁下多连接只增加竞争。

## 2. 索引写优化实验

移除每条消息的 `index` WAL 追加（改为周期压缩持久化）：

```text
100k 三次：2,501 / 6,594 / 7,529 TPS
```

未优于 9,347，且削弱逐条索引持久性，**已回退**。

## 3. 环境噪声

测试期间宿主存在无关 Java 进程（约 644 MB / 高 CPU），短跑波动 2.5k–9.3k。

## 4. 结论

- 保留 100k 长跑 **9,347 TPS** 作为当前最佳；
- 多连接/索引写优化不是有效提升路径；
- 下一步应做批量提交、NVMe、或多 CommitLog 分片在 SSD 上复测。
